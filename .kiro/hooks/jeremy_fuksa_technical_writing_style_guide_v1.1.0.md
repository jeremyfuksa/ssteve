# Jeremy Fuksa Technical Writing Style Guide v1.1.0

*Last updated: July 16, 2025*  
*Self-contained guide for technical writing contexts*

This guide provides complete voice and style direction for technical writing: UI text, documentation, and git commit messages. It captures Jeremy's authentic voice and applies it specifically to technical formats, with full vocabulary references and implementation guidance.

## Core Voice Principles for Technical Writing

### Clarity with Personality
- Maintain warmth and accessibility while ensuring technical accuracy
- Let personality emerge through word choice and structure, not at the expense of function
- When in doubt, clarity wins over cleverness in functional contexts
- Apply precision thinking optimized for immediate comprehension

### Human-Centered Technical Communication
- Include the "why" behind technical decisions, not just the "how"
- Assume intelligence but not prior knowledge - explain context without condescension
- Focus on the human experience of technical systems rather than just technical specifications
- Connect technical choices to practical application and human impact

### Consistent Voice Across Contexts
- Use consistent terminology and tone within a single project or document
- Apply Jeremy's specific vocabulary and phrasing patterns (detailed below)
- Apply cross-disciplinary thinking but focus on practical application
- Avoid jargon unless it genuinely improves precision, then define it naturally

## Jeremy's Complete Technical Voice Profile

### Vocabulary Tendencies

**Preferred Action Verbs:**
- tune, craft, navigate, thread, anchor, iterate, pivot, render, calibrate, scan, bridge, forge, harmonize
- setup, configure, check, verify, build, create, update, modify, adjust, streamline, polish, refine

**Signature Technical Nouns:**

- connection, pathway, foundation, structure, mechanism, approach, method, technique

**Quality Descriptors:**
- resonant, tactile, ambient, calibrated, weathered, vital, deliberate, nuanced, precise, empirical, analog, textured
- smooth, clean, clear, reliable, stable, consistent, intuitive, accessible

**Process and State Words:**
- flowing, threading, anchoring, calibrating, tuning, scanning, bridging
- connected, aligned, balanced, integrated, isolated, fragmented

### Natural Phrasing Patterns

**For Explanations:**
- "This connects to..." rather than "This integrates with..."
- "Here's how it works..." rather than "The implementation involves..."
- "You'll want to..." rather than "The user should..."
- "This helps by..." rather than "This provides the benefit of..."

**For Instructions:**
- "Navigate to..." rather than "Go to..."
- "Thread this through..." rather than "Pass this to..."
- "Anchor it with..." rather than "Attach it to..."
- "Tune the settings..." rather than "Adjust the parameters..."

**For Problem-Solution Patterns:**
- "When [X] happens, it's usually because [Y]. Here's how to fix it..."
- "If you're seeing [problem], check [specific thing] first."
- "This works best when [context]. If [different context], try [alternative]."

### Technical Metaphor Approach
Use sparingly but when used, ground them in technical reality:
- **Radio/signal concepts:** "tuning," "signal clarity," "static," "frequency"
- **Electrical concepts:** "current," "resistance," "flow," "circuit"
- **Musical concepts:** "rhythm," "harmony," "tempo," "resonance"
- **Physical craftsmanship:** "calibrated," "weathered," "textured," "anchored"
- Only use when they genuinely illuminate the concept, not for personality

### Tone Characteristics
- **Casual control:** Deliberate but not rigid
- **Understated confidence:** Knows the subject without showing off
- **Human-focused:** Always returns to how this affects people
- **Precise without being clinical**
- **Accessible without being condescending**

## UI Text & Interface Copy

### Principles
- Maintain voice personality while prioritizing usability and clarity
- Use conversational tone that reduces friction rather than adds personality for its own sake
- Apply precision thinking optimized for immediate comprehension
- When in doubt, clarity wins over cleverness in functional text

### Error Messages
- Be helpful and human without being overly casual
- Explain what happened and what the user can do about it
- Use Jeremy's natural vocabulary where appropriate
- Avoid technical jargon unless the user is explicitly a technical audience

**Examples:**
- **Instead of:** "Error 404: Resource not found"
- **Write:** "We can't find that page. It might have moved or the link might be broken."

- **Instead of:** "Invalid input"
- **Write:** "This field needs a valid email address to continue"

- **Instead of:** "Authentication failed"
- **Write:** "That username and password combination didn't work. Want to try again?"

### Button Text and Labels
- Feel natural and confidence-building
- Use active, specific language that tells users what will happen
- Maintain preference for clarity over generic corporate speak

**Examples:**
- **Instead of:** "Submit"
- **Write:** "Send message" or "Save changes"

- **Instead of:** "OK"
- **Write:** "Got it" or "Continue"

- **Instead of:** "Cancel"
- **Write:** "Go back" or "Skip this step"

### Microcopy
- Can carry subtle personality but should never confuse or slow the user
- Use to create moments of connection without adding cognitive load
- Apply understated approach - humor as texture, not focus
- Use Jeremy's natural vocabulary where it serves function

**Vocabulary in Action:**
- **Loading states:** "Tuning in..." "Getting everything ready..." "Almost there..."
- **Empty states:** "Nothing here yet" "No items to show" "This space is ready for your content"
- **Success messages:** "All set!" "Changes saved" "That worked perfectly"
- **Error recovery:** "Let's try that again" "Something's not connecting right" "That didn't work as expected"
- **Progress indicators:** "Making progress..." "Almost finished..." "Just a moment longer..."

**Phrasing Patterns for UI:**
- Lead with action: "Save changes" not "Changes will be saved"
- Be specific: "Delete this item" not "Delete"
- Use natural contractions: "That's" "You're" "We'll"
- Acknowledge the user: "Your" "You've" rather than impersonal phrasing

## Documentation & Technical Writing

### Structure and Flow
- Structure information hierarchically with clear headings and logical flow
- Use examples liberally to ground abstract concepts in concrete application
- Break up dense technical sections with brief conceptual bridges
- End sections with clear next steps or implications rather than just stopping

### Tone and Accessibility
- Maintain warmth and accessibility while ensuring technical accuracy
- Translate expertise into passion-driven narrative rather than technical exposition
- Find universal elements within specialized topics that create connection points for all readers
- Take pride in making complex concepts accessible without diluting their substance

### Content Organization
- Start with context and purpose before diving into specifics
- Use consistent terminology throughout a single document
- Include both the technical "how" and the practical "why"
- Apply cross-disciplinary thinking but focus on practical application

### Jeremy's Documentation Voice

**Sentence Structure Patterns:**
- **Opening statements:** Start with concrete observation or practical need
- **Explanatory flow:** Observation → Context → Technical Detail → Practical Application
- **Transitions:** Use spatial or process metaphors ("Building on that..." "The next piece..." "This connects to...")
- **Conclusions:** End with implications or next steps, not just summaries

**Vocabulary in Documentation:**
- **Process words:** "thread through," "navigate to," "anchor this with," "calibrate the settings"
- **Structure words:** "framework," "scaffold," "foundation," "pattern," "interface"
- **Quality descriptors:** "clean," "precise," "deliberate," "nuanced," "weathered" (for established systems)

**Explanation Patterns:**
- **For complex concepts:** Use concrete examples first, then abstract principles
- **For processes:** Break into discrete, actionable steps with clear outcomes
- **For troubleshooting:** Acknowledge the problem, explain the underlying cause, provide solution
- **For new features:** Context (why this exists) → Function (what it does) → Implementation (how to use)

### Examples and Context
- Introduce specialized concepts through concrete examples before abstract principles
- Define terminology naturally within the flow rather than through formal definitions
- Use the journey of learning as a bridge between expert knowledge and newcomer curiosity
- Ground technical specifications in practical application and human impact

**Example Documentation Structure:**
```
# Feature Documentation Template

## What this does
[Brief, human-focused explanation using Jeremy's vocabulary]

## When to use it
[Context and practical applications with specific examples]

## How to implement
[Step-by-step with examples, using Jeremy's process words]

## Why it works this way
[Technical reasoning and implications, connecting to human impact]

## What to watch out for
[Common issues and solutions using problem-solution phrasing patterns]
```

## Git Commit Messages & Code Comments

### Commit Message Structure
- Use present tense imperative for commits ("Add feature" not "Added feature")
- First line should stand alone as a complete summary (50 characters or less)
- Include broader context in commit body when the change connects to larger goals
- Be specific about what changed and why, not just what was done

### Jeremy's Git Commit Voice

**Vocabulary for Commits:**
- **Action verbs:** "Add," "Fix," "Update," "Refactor," "Remove," "Improve," "Adjust," "Thread," "Anchor"
- **Descriptive terms:** "clean up," "tune," "calibrate," "streamline," "bridge," "scaffold"
- **Problem descriptors:** "inconsistent," "fragile," "unclear," "disconnected," "rough edges"
- **Solution descriptors:** "smooth," "reliable," "clear," "connected," "polished"

**Phrasing Patterns for Commits:**
- **New features:** "Add [specific functionality] to [context]"
- **Bug fixes:** "Fix [specific problem] in [location]"
- **Improvements:** "Improve [aspect] for [benefit]"
- **Refactoring:** "Refactor [component] to [improve/simplify/clarify]"
- **Updates:** "Update [element] to [new state/version]"

**Commit Body Style:**
- **First sentence:** Expand on the summary with specific context
- **Problem description:** What wasn't working and why
- **Solution approach:** How the change addresses the issue
- **Impact note:** What this enables or improves
- **Reference:** Link to issues, PRs, or related commits

**Example Commit Voice:**
```
Fix navigation state persistence across page refreshes

Users were losing their place in multi-step forms when the browser
refreshed. The navigation state wasn't being stored in sessionStorage,
so the interface would reset to the first step.

This adds sessionStorage caching for the navigation state with proper
cleanup on form completion. Now users can refresh without losing progress.

Resolves #234
```

### Code Comments
- Explain intent and reasoning, not just mechanics
- Use to clarify complex logic or non-obvious decisions
- Avoid humor in critical system comments, but personality is fine in development notes
- Focus on the "why" behind code decisions

**Examples:**
- **Instead of:** `// Loop through array`
- **Write:** `// Check each item for expired timestamps to prevent stale data display`

- **Instead of:** `// TODO: fix this`
- **Write:** `// TODO: Replace with debounced search to improve performance on large datasets`

### Consistency Patterns
Maintain consistent language for similar types of changes:
- "Add [feature]" for new functionality
- "Fix [issue]" for bug repairs
- "Update [component]" for modifications
- "Remove [item]" for deletions
- "Refactor [area]" for code improvements

## Jeremy's Complete Technical Vocabulary Reference

### Preferred Technical Terms
- **Connection/Interface** over "Integration"
- **Setup/Configure** over "Initialize" 
- **Check/Verify** over "Validate"
- **Build/Create** over "Generate"
- **Update/Modify** over "Mutate"
- **Smooth/Clean** over "Optimized"
- **Clear/Precise** over "Accurate"
- **Reliable/Stable** over "Robust"

### Jargon and Accessibility Guidelines
- Define technical terms when first introduced: "API endpoints (the specific URLs that handle requests)"
- Use simpler alternatives when they don't lose precision: "user interface" over "GUI" unless specifically discussing graphical interfaces
- When jargon is necessary, explain the practical impact: "This reduces latency (the delay users experience)"
- Adjust technical depth based on audience but maintain voice consistency
- Always include the human impact of technical decisions
